## Introduction & Criteria
Assignment 1 listed requirements detailing a Pokémon battling system. The basic requirements of the system included:
- The ability to process commands such as `removeSeed` and `setSeed`
- Supporting the creation of Pokémon with stats, skills, names, and certain actions
- Support for dynamic run-time classes and objects
- Managing battles between two Pokémon

*A more detailed description of the requirements can be viewed in the assignment one description. (1)*

This document analyzes and compares the class diagrams generated by groups 40, 57, and 68 in order to distinguish which diagram suits the requirements of the system. The following criteria will be used in the evaluation:
- Requirement Coverage - Whether the class diagram captures the system requirements.
- Class Design Quality - Whether each class is cohesive and correctly encapsulates relevant attributes and methods. Also considers whether abstractions and inheritance are used effectively.
- Relationship Integrity - Whether the designated relationships make sense in the context of the system and requirements.
## Comparative Analysis
### Commonalities
Each class diagram (D40, D57, and D68) includes a Pokémon class with attributes for name, seed, and win/loss counts, along with methods to update those attributes. This design allows each Pokémon to track its own record rather than relying on the battle system. The inclusion of the seed attribute also enables independent random number generation for each Pokémon instance. These commonalities strengthen the requirement coverage and class design quality (particularly cohesion and encapsulation) by supporting more autonomous Pokémon.
### Differences
#### The Command Processor
All three class diagrams handle input processing via a dedicated class. D57 names this class CommandManager, but for consistency this document will refer to the CommandManager and CommandProcessor classes as **CP**. 

The CPs in D40 and D57 have a single method `processCommand` that fails to describe the actions the system might take when executing different commands. D68 shows a more thorough design of a command processor that is supported by helper methods like `handleSetSeed` and `handleBattle`, which explicitly show support for the commands listed in the requirements.
#### Dynamic Runtime Classes and Instances
D40 does not provide support for generating Pokémon dynamically at run time, and therefore fails to meet that requirement. D57 accomplishes this task via the Pokédex class, which uses the `getPokemonByName` method to create or fetch instances of Pokémon through an API or some data set. One weakness of D57's approach is the lack of cohesion in this method, since `getPokemonByName` would contain logic for both creating and fetching a Pokémon from the existing list. D68 has the most elegant solution via the PokémonFactory which utilizes reflection.
#### Persistence
Although not explicitly stated in the requirements, the existence of the win and loss attribute requirements imply the need for Pokémon to persist between battles. Without persistence, the win and loss ratios would be meaningless because new Pokémon would be generated for every battle. D57 is the only diagram which provides a solution to this implied requirement via the `pokemonList` in the Pokédex class. This allows Pokémon to participate in more than one battle, which contextualizes the win and loss attributes.
#### Skills
All three class diagrams handle Pokémon skills through a dedicated class. D57 names this class Move, but for consistency this document refers to it as Skill and the corresponding enumerations (MoveType in D57 and ActionType in D68) as SkillType.

D40 identifies attacking and defending skills by utilizing two subclasses of Skill. However, these subclasses don't provide meaningful additional attributes or methods, making the subclasses largely superficial. D57 and D68 chose to use an enumeration in order to differentiate between attacking and defensive skills. This approach is stronger due to its more object oriented nature, and it allows other classes to reference the enumeration if needed. However, it is worth noting that the enumeration could be simplified to a boolean given that there are only two values.

In D57 and D68, Pokémon have the ability to process skills that are used on them via the `applyMove` and `receiveDamage` methods. This is a strong approach as it allows the Pokémon itself to determine the moves applied damage, which might be reduced by an active defensive move or the Pokémon's defensive stats. In contrast, D40 passes an integer to the `evaluateDamage` method. This approach works, but might need more information about the skills type or other properties of the opposing skill to be processed correctly. D57 and D68 therefore have the stronger approach.
#### The Skill Buffer
Due to the nature of defensive skills and the turn order listed in the requirements, it is sometimes necessary that the defending Pokémon 'carry' its used skill into the next round of battle. D57 and D68 addressed this requirement with the `moveBuffer` and `lastDefenseSkillUsed` attributes, which stores a skill so that they can be processed in the next round of combat. D40 addressed this same issue by adding a `defenseBuff` integer to the Stat class, which would be actively managed by the Pokémon on each of its turns. This is an elegant solution, but does reduce the cohesion of the Stat class since it now is concerned about battle statistics, and not just the Pokémon's stats. Additionally, the choice to make `defenseBuff` an integer results in loss of information about the actual defensive skill that was used.
#### Stats
D40 and D57 separate Pokémon Stats into the Stats class, rather than including them as attributes in the Pokémon class like D68. One strength of separating the stats into their own class is that it allows Pokémon to focus on performing high level actions like attacking and defending without having to worry about specific calculations (i.e. it simplifies the Pokémon class). It does however add a small amount of complexity to how the stats will be applied to skills, as they now have to be accessed through the stats object. 
#### Relationships
D40 struggles to convey a meaningful relationship between the CP and Pokémon classes. The one-to-one association is somewhat ambiguous, as it could imply that Pokémon depend on a CP or that a CP directly controls a Pokémon. However, the decision to separate the RandomNumberGenerator class and allow all Pokémon to depend on it is a strong design choice. This approach supports cohesion by isolating random number generation into a dedicated utility. 

D57 manages to convey the relationship between the CP and the rest of the system with more clarity. Each CP contains a BattleManager that depends on the Pokédex class to properly provide access to the creation and fetching of Pokémon, while also being able to configure each BattleManager with a seed.

Similarly to D57, D68 establishes a relationship from the CP to the PokemonFactory and BattleReferee classes to accomplish the same goal. However, D68 allows for a single CP to manage multiple BattleReferees, which could aid in handling future requirements.

## Rankings and Conclusion
D57 meets the requirements outlined in Assignment 1 and successfully addresses several implied requirements, such as persistence and skill buffering. The Pokédex class provides an elegant solution for the dynamic creation and persistence of both Pokémon and Skills, which was not addressed by D40 or D68, making D57 the strongest overall design. 

D40 ranks as the weakest diagram due to its limited flexibility, potential for losing information about defensive skills, and lack of persistence or runtime Pokémon creation. D68 comes close to the top with a superior CP that clearly supports the required commands, but falls short of D57 because it does not implement persistence for Pokémon or Skills.

**Final Rankings**:
1. D57 (Best)
2. D68 (Middle)
3. D40 (Worst)
## Diagram Feedback
Listed below are suggestions for improvements to each diagram. These are optional design decisions, but they would likely improve clarity, maintainability, and alignment with the system requirements.
#### D40
- Add more detailed methods to the CommandProcessor to show support for each required command.
- Add persistence for Skills and Pokémon to allow them to retain information across multiple battles.
- Combine the attack and defending skill lists in the Pokémon class into a single list of Skills.
- Use a buffered skill instead `defenseBuff` to keep the Stat class more cohesive and hold onto information about the entire defensive skill, not just the power.
#### D57
- Add more detailed methods to the CommandProcessor to show support for each required command.
- Add a `createPokemon` method to the Pokémon, so that `getPokemonByName` does not have to potentially create Pokémon (or is at least supported by the `createPokemon` method).
- Change the MoveType enumeration into a boolean on the Move class signifying whether it is an attacking move or not, unless more types are introduced in the future.
#### D68
- Add persistence for Skills and Pokémon to allow them to retain information across multiple battles.
- Change the ActionType enumeration into a boolean on the Skill class signifying whether it is an attacking move or not, unless more types are introduced in the future.
- Consider how the CommandProcessor needs to interact with the BattleReferee to set its seed and begin the battle.
